# ADR-0001: декомпозиция по бизнес-возможностям

- Статус: принято
- Дата: 2026-10-02

## Контекст

Маркетплейсу нужны управление пользователями и каталогом, персональная лента,
заказы, платежи и уведомления. Учебный проект должен ясно показать границы
ответственности и владение данными, но не требует работающей бизнес-логики или
промышленной платформы эксплуатации.

## Решение

Выделить по сервису на каждую бизнес-возможность: Identity, Catalog, Feed,
Order, Payment и Notification. Доступ клиентов направить через тонкий API
Gateway. У каждого бизнес-сервиса своя логическая база данных. Команды и
запросы, которым нужен немедленный ответ, выполнять синхронно по REST;
информирование независимых потребителей — событиями через RabbitMQ.

В этой итерации инициализируется только API Gateway. Он содержит исключительно
`GET /health`; маршрутизация и бизнес-операции остаются архитектурным проектом.

## Последствия

Положительные:

- границы совпадают с формулировкой задания и легко объясняются;
- каталог, ленту и уведомления можно масштабировать независимо;
- платежные данные изолированы от остальных данных;
- события уменьшают связанность уведомлений и построения ленты с заказами.

Отрицательные:

- оформление заказа требует согласования нескольких сервисов и компенсаций;
- появляется eventual consistency для ленты и уведомлений;
- по сравнению с монолитом сложнее локальный запуск, наблюдаемость и контракты.

Принятые ограничения сложности:

- один брокер, один протокол синхронных вызовов и один тип SQL-хранилища;
- нет Kubernetes, service mesh, CQRS-фреймворка и отдельного recommendation/ML
  сервиса;
- персонализация остаётся внутри Feed Service и использует прозрачную формулу,
  а не ML-модель.
